# 风格示例

只有在需要模仿具体句式时读取。本文件的默认示例是中性技术解读。

## 中性技术解读（默认）

### 开头：时间线

> 从 Agent 元年开始，Agent 的工程对象逐步从单次模型调用，扩展到上下文管理、工具运行时、长时任务和多 Agent 编排。每一步都没有替代前一步，只是把控制边界向外推了一层。

### 开头：问题定义

> 当 Agent 接入文件系统、网络和代码执行环境后，提示词已经无法独自承担权限、状态、验证和审计。需要把这些职责拆到运行时组件中处理。

### 解释系统边界

> Prompt 决定单次调用的指令和输出格式。Context 决定模型当前可见的信息。Harness 则管理工具调用、错误恢复和可观测性。三者解决的问题不同，不能用一段 system prompt 替代。

### 解释条件与限制

> Loop 适合具有明确验收信号的重复任务。若无法定义完成条件，系统无法可靠地判断应继续执行、停止还是移交给人，此时不宜直接进入无人值守模式。

### 收尾

> 对多数团队而言，优先补齐评测、状态管理和权限边界，比增加 Agent 数量更有实际价值。只有在存在真实的并行、依赖传播或独立审查需求时，再考虑图式编排。

### 用词替换

| 避免 | 使用 |
| --- | --- |
| 这个设计彻底颠覆了 Agent | 这个设计把 Agent 的控制流显式化 |
| Prompt 已经过时 | Prompt 仍适合处理单次调用的指令与格式 |
| 终于进入 Agent 时代 | Agent 开始承担多步骤任务后，工程关注点发生了变化 |
| 这是系统的护城河 | 这部分通常决定系统的可维护性和可靠性 |
| 这意味着什么 | 该变化带来的直接影响是 |

## 实战笔记体（仅显式启用）

### 开头：真实场景

> 这次任务卡在工具调用上。模型能给出计划，但连续两次把参数传错。问题不在模型能力，而在 schema 和返回值没有把约束表达清楚。

### 过程：决策与验证

> 工具层没有继续加提示词，而是把参数校验放到 gateway。之后用同一批任务回归，确认错误参数不再进入执行环境。这个改动影响的是运行时约束，不是模型本身。

### 收尾：保留限制

> 这套做法先解决了参数错误的问题，但长任务的状态压缩还不稳定。下一步需要把中间产物外置，并补充跨轮次的回归用例。

## 不可使用的示例

- 未经用户提供的第一人称经历、实验或情绪反应。
- “终于”“炸裂”“封神”“颠覆”“碾压”等无证据强化词。
- 吐槽、反问、感叹式独立短段，除非用户明确要求实战笔记体并提供了真实语境。
